## 2. 対立的検証 — 攻撃可能な穴（優先度順）

### 攻撃1【急所】アプリ側 PQ エンコード起因の可能性が未排除

- scRGB 経路: FP16 → PQ 変換は**表示パイプライン側**が実施
- HDR10 経路: PQ コード化は**アプリ側**（Qt RHI / シェーダ）が実施し、変換済みの値がバックバッファに入る
- したがって「scRGB 正確・HDR10 不正確」という観測は、**「アプリの PQ エンコードが不正確、ドライバは正確」でも完全に説明可能**
- バックバッファ内容の直接読み出し（Readback / PIX 等）でランプが欠落なく格納されている証拠が、投稿・リポジトリ双方に無い

### 攻撃2 「3台ビット一致」は 2 仮説を区別しない

- 3 台とも同一テストアプリを実行 → 決定的なアプリ側変換バグでも、決定的なドライバ LUT でも「全台ビット一致」は予測される。識別力なし
- さらに Laptop は "Hardware: Independent Flip"、RTX PRO は "Hardware **Composed**: Independent Flip"（MPO 経由）と**提示経路が異なるのに出力がビット一致** → むしろ「欠陥はバッファ格納時点で存在」説とも整合（スキャンアウト LUT 段が両経路で共有されていれば駆動側説でも説明可能なため、決定打ではない）

### 攻撃3 Composed Flip 対照は「DWM が ±1 忠実」という仮定に依存

- 同じ対照で黒付近に 23 個の新スキップが発生 → DWM がコードを改変することは実証済み
- DWM が空間ディザ・平滑化を掛けていれば、バッファ内の 2 コード段差が均されて「消えた」ように見える余地
- 合成時の 60 フレーム時間解析（画素変動 0 か）が未報告

### 攻撃4 Ampere 対照は世代対照として成立していない

- Ampere はリンク 10bpc でも内部 8bit + ディザで動作 → **真 10bit スキャンアウトモードでの計測ができていない**
- 「どの世代でも真 10bit に入れば同じ量子化器を通る。Blackwell は真 10bit に入るようになっただけ」という反論が可能
- 投稿 #6 自体は「Ampere では評価不能」と正確に記述している。主張は「Blackwell に固有」ではなく「Blackwell で観測、他世代は真 10bit で未評価」に留めるべき

### 攻撃5 スレッド元現象との同一性が未実証

- 元投稿者 (octatecreations) の再現手段: Microsoft D3D12HDR サンプル（+ banding-test-pattern ブランチ）
- 当方の計測: Qt Quick (D3D11 RHI) アプリ
- 同一サンプルで同じ 49 ジャンプが出ることは未確認 → 「別件」として扱われるリスク

### 攻撃6【軽微】条件の単一性

- 全計測が 2160p / 23.976 Hz の 1 モード。LUT 構成がタイミング依存の可能性は未排除
- フラットパッチの「+1 コード」は期待値計算の丸め規約差でも説明可能。証拠としては弱い（主張から外すか脚注扱いに）

## 3. 反論を封じる追加実験（優先度順）

### 実験 A【最優先・攻撃1と2を同時に潰す】シェーダ変換を通さない直接コード書き込み

- 10bit PQ コードを CPU 側で整数として直接生成し、staging texture → R10G10B10A2 バックバッファへ CopyResource で転写（シェーダ・レンダーパスを一切通さない）
- フルスクリーン Independent Flip でキャプチャ
- 判定: ジャンプが残る → アプリ側説は死亡、ドライバ/ハード側確定。消える → 現行アプリの PQ エンコードに欠陥（先に修正）
- 併せて現行アプリでもバックバッファ Readback を実装し、格納コードの完全性を CSV で証明する

### 実験 B【攻撃5を潰す】元投稿者と同一サンプルのキャプチャ

- allenwp/DirectX-Graphics-Samples の banding-test-pattern ブランチ（および無改変の D3D12HDR）をビルドし、同一チェーンでキャプチャ
- 判定: 同一コード位置のジャンプが出れば、スレッド現象との同一性が確立

### 実験 C【攻撃3を補強】Composed Flip 時の時間解析

- 合成経路のキャプチャ 60 フレームで per-pixel min/max/変動画素数を算出し、ディザの有無を明示

### 実験 D【攻撃6に対応・余力があれば】60 Hz での再計測

- 2160p60（キャプチャ機の対応モードに合わせる）で 1 系統だけ再計測し、タイミング非依存を示す

### 実験 E【他社対照・無料】ROG STRIX 内蔵 Intel iGPU での計測

- 目的: 他社 GPU の線上コードが欠落なく出ることを示し、アプリの PQ エンコードと計測チェーン（DeckLink・解析スクリプト）の健全性を同時に証明する（攻撃 1 の補強）。元スレッドの「Intel 内蔵では再現しない」（パネル写真ベース）を線上コードで裏付ける
- 成立条件（実施前に順に確認。不成立なら本実験は中止し報告から外す）:
  1. **端子配線**: 外部出力端子のうち iGPU に配線されたもの（USB-C 側が多いが機種依存）を特定する。確認は Windows のディスプレイの詳細設定で当該ディスプレイの「接続先 GPU」表示、または NVIDIA CP の PhysX 接続図。HDMI 端子が dGPU 直結の場合、その端子では iGPU の表示パイプラインは計測できない
  2. **実行 GPU の固定**: 設定 → グラフィックスでテストアプリを「省電力（Intel）」に固定。dGPU レンダリング + iGPU 出力のクロスアダプタ構成は対照として不純なため避ける
  3. **リンク条件**: 2160p23.976・RGB 4:4:4・10bpc・PQ InfoFrame が張れること。USB-C → HDMI 変換は実績のある CAC-1088 を使い、フラットパッチで健全性を先に確認（旧世代アダプタの InfoFrame 落ち・パッキング破壊に注意）
- 手順は既存 PROCEDURE.md を踏襲（DeckLink 検出表示の確認、PresentMon 並走による提示経路記録を必須とする）
- 留意: Intel iGPU が内部ディザ（Ampere 型の 8bit 格子等）を使う場合は真 10bit 評価不能となる。その場合は結果を報告に含めず、AMD 対照（購入判断は保留中）の要否判断材料とする
- 判定: 真 10bit で欠落ゼロなら攻撃 1 への追加証拠となり、AMD GPU 購入の必要性はほぼ消える

## 4. 実装時の注意（Claude Code 向け）

- 実験 A は既存パターンツールへのモード追加が最小工数（ウィンドウ・スワップチェーン生成は既存流用、描画のみ CopyResource に差し替え）。ただし Qt RHI がバックバッファへの直接コピーを許すか要確認。不可なら素の D3D11 で最小ツールを別途書く方が確実
- Readback は Present 直前のバックバッファに対して行うこと（表示パイプライン到達前の値を証明する目的のため）
- 期待値テーブル（PQ コード ⇔ nit）は既存 data/ の生成スクリプトと同一の丸め規約を使い、規約を README に明記（攻撃6対策）
- PresentMon の並走ログ取得は既存手順（PROCEDURE.md）を踏襲。実験 A/B でも提示経路の記録を必須とする
- キャプチャ解析スクリプトは既存の ramp 行解析を流用し、出力（ジャンプ位置リスト）が既存 data/m25_summary.json と直接比較できる形式にする

## 6. 進捗記録（2026-09-11、Claude Code）

### 6.1 既存データだけで詰められた点

- **攻撃 3（DWM のディザ）は既存データで否定できる。** `data/m25_hdr10_composed_ramp_row.csv` は
  孤立 1px 反転 0・非単調 0・フレーム間変動 0（`tools/ramp_report.py` で再計算）＝ DWM 経路に空間・時間ディザは無い。
  ディザ無しなら「バッファコード → 線上コード」は決定論的な単調写像 f で、|f(k)−k| ≤ 2。バッファに欠落 k があれば
  出力にも欠落が残り、それを閉じるには f がそこで 1 段落ちる必要がある。落ちた分は別の場所で 1 段上がらねばならず、
  上がった場所には新しい欠落が出る。合成時の中間調（コード > 144）に欠落はゼロなので、49 個の中間調欠落を
  合成が「均した」ことはあり得ない → **中間調の欠落はバッファに無い**、は既存データからも言える。
  ただし合成経路は ±1 忠実ではない（段幅 6/9/10・近黒 23 欠落）ので、決定打は依然として実験 A。
- **攻撃 6（丸め規約）:** `tools/dither_analyze.py` の期待コード定数 `0.7518` は **1000 nit** の PQ 値だった
  （2000 nit は 0.8274 = 846.5/1023）。期待コード比較だけが 10% 低く出ていた（段幅・飛び数・欠落一覧・単調性には無関係、
  RESULTS §1 の平坦パッチ期待値は正しい）。`pq.py` から算出するよう修正済み。
- **攻撃 2 補足:** rog6000 は `Hardware Composed: Independent Flip`（MPO プレーン）で m25 の `Hardware: Independent Flip`
  と 3840 px・16 パッチともビット一致（`ramp_report.py --ref` で再確認: 差 0 px）。

### 6.2 実装したもの

- `tools/hdr10_direct.cpp`（素の D3D11・MinGW でビルド）: 実験 A のツール。整数 PQ コードを CPU 生成 → DEFAULT
  テクスチャ → `CopyResource` で R10G10B10A2 バックバッファへ。N 回に 1 回 Present 直前に読み戻してソースと
  バイト比較、ランプ行を CSV 出力。`--mode scrgb`（FP16・同経路）を対照に持つ。手順は PROCEDURE.md §9。
  Qt RHI はバックバッファへの直接コピーを公開しないので、§4 の助言どおり素の D3D11 で書いた。
- `tools/ramp_report.py`: npz / CSV → `data/*_summary.json` と同形式の要約（段幅・飛び・欠落・ディザ指標・
  期待コード比較・参照 CSV とのビット比較・PresentMon の PresentMode 集計）。m25 の数値を再現することを確認。
- スモーク（ROG・RTX 5090 上の PA32UCDM・60 Hz・DeckLink 未接続）: 窓・全画面とも読み戻しがソースとビット一致
  （全画面 3840×2160・色空間サポート 0x3）。PresentMon は非管理者では動かない（警告のみで CSV 無し）。

### 6.3 実験 A 本番（2026-09-11 22:40〜、結果: ジャンプ残存 → アプリ側説は死亡）

- 経路: RTX PRO 6000（616.56・TB5 eGPU）→ DP 2.1 → CAC-1088 → HDFury Vertex（EDID 偽装）→ UltraStudio 4K Mini。
  信号 2160p23.98 RGB444 10bit PQ。PresentMon（管理者）並走: 1563/1568 Present が Independent Flip（5 件はウィンドウ生成時）。
- HDR10: バックバッファ読み戻し 80/80 ビット一致（全コード 0..846 格納・飛び 0）。線上は **m25 / rog6000 と同じ 49 コードが
  欠落**（一覧が完全一致）、段幅 4/5/9/10、線上−ソース {−1: 14, 0: 2475, +1: 1351}、平坦パッチ 11/16 が +1。
- scRGB 対照（同経路・FP16）: 中間調の欠落ゼロ、線上−ソース {−1: 275, 0: 3565}。近黒 14 コード（≤135）の欠落は表示側
  FP16→PQ 再符号化の ±1 精度が離散ランプで露出したもの（`m25_hdr10_composed` の近黒 23 欠落と同じ出口段）。
- 同夜 23:26〜 **RTX 5090 Laptop**（8/30 の個体・616.56）でも実施: HDMI → UltraStudio 直結、PresentMon 1564/1571・1505/1510 が
  `Hardware: Independent Flip`（MPO 無し）。取り込み全フレームが RTX PRO 6000 の結果と両スワップチェーンとも**ビット一致**
  （`data/a5090_*`）。途中、Vertex 経由では RTX 5090 が HDCP 2.2 を掛けて全画素 0 になった（PROCEDURE §8 の 8）。
- 判定: §3 実験 A の基準「ジャンプが残る → アプリ側説は死亡、ドライバ/ハード側確定」に該当。**§5 の条件を満たしたので
  正式報告へ進める**（文案: `docs/report_drafts.md` §1e）。攻撃 1・2 は閉じた。データ `data/a_*`、詳細 RESULTS.md §9。
